# API 흐름을 설계하거나 큰 Service 메서드를 나눌 때 확인 규칙

`service.md`의 개별 규칙(레이어 경계, 즉시계산, 조회 서비스 재사용)은 사실 이 문서의 어휘로
설명되는 구체적 사례들이다. 새 API 흐름을 처음 설계하거나, 이미 있는 Service 메서드가
길어져서 나누고 싶을 때 이 문서를 먼저 읽는다.

## 어휘

- **Module(모듈)**: 인터페이스와 구현을 가진 모든 것. 메서드 하나일 수도, Service 클래스
  하나일 수도 있다.
- **Interface(인터페이스)**: 호출부가 알아야 하는 모든 것 — 파라미터/반환 타입뿐 아니라
  호출 순서, null 허용 여부, 트랜잭션 경계까지 포함한다.
- **Depth(깊이)**: 작은 인터페이스 뒤에 얼마나 많은 동작이 숨어 있는가. 인터페이스가
  구현만큼 복잡하면 **얕다(shallow)**, 인터페이스는 단순한데 뒤에서 많은 일을 하면
  **깊다(deep)**.
- **Seam(경계)**: 인터페이스가 놓이는 자리. 어디에 경계를 그을지는 그 자체로 별도의
  설계 판단이다 — "무엇을 감출지"와 "어디서 감출지"는 다른 질문이다.
- **Deletion test**: 이 메서드/Service를 지웠다고 상상해본다. 복잡도가 사라지면
  pass-through(있으나 마나)였던 것이고, 호출부 여러 곳으로 다시 퍼지면 제 역할을
  하고 있던 것이다.

## Controller → Service 단계별 분해 규칙

경로 탐색·집계처럼 "외부 API 호출 → 후보 선별 → 관련 정보 전체 조합 → 응답 변환"
같이 여러 의미 단계를 거치는 흐름은, **각 단계가 이름 있는 메서드나 별도 Service로
분리되어 메서드 목록만 보고 전체 흐름을 파악할 수 있어야 한다.**

기준:

- 한 메서드 안에 "무엇을 위해 이 코드가 있는지" 질문이 2번 이상 필요하면, 그 지점이
  seam 후보다.
- 이미 존재하는 seam(예: `RestStopAggregateQueryService`)으로 흡수될 수 있는 새 필드는
  거기 넣는다. 새 외부 연동이거나 완전히 다른 책임이면 새 seam을 어디에 둘지 먼저
  정한다 — DTO에 `with*()`를 하나 더 붙이는 것으로 때우지 않는다(`service.md`
  "즉시 계산 가능한 값은 생성 시점에 포함" 참고).
- **어댑터 1개는 가상의 seam, 2개부터 진짜 seam이다.** 지금 당장 하나뿐인 구현을
  위해 인터페이스를 미리 파두지 않는다(YAGNI) — 실제로 두 번째 사용처가 생기거나,
  단계 자체가 독립적으로 테스트/이해되어야 할 만큼 무거워졌을 때 분리한다.

### 케이스: `RouteRestStopService.findRouteRestStops`

현재 이 메서드 내부에 아래 4단계가 private 메서드로 나뉘어 있지만, 어떤 메서드가
어느 단계에 속하는지는 메서드 이름만으로 완전히 드러나지 않는다.

1. 목적지 좌표 계산 (`resolveDestination`)
2. 카카오 길찾기 API 호출 → 경로 좌표 목록 (`kakaoMapClient.directions(...)`)
3. 경로 근처 휴게소 후보 탐색 (`restStopsOnRoute`, `buildCandidate`)
4. 후보들의 `service_area_code`로 전체 연관 정보 조합 (`RestStopAggregateQueryService`,
   이미 분리됨) → 응답 DTO 변환

4번은 이번 세션에 이미 별도 Service(`RestStopAggregateQueryService`)로 분리됐다 —
이게 이 규칙이 말하는 "deep module"의 실제 사례다: 호출부는 `(codes, adminOverridden)`
하나만 알면 되고, EV차저/이미지/테마/이벤트/연관정보 5개 조합은 인터페이스 뒤에 숨어있다.

1~3번은 아직 한 클래스 안에 뒤섞여 있다. 다음에 이 메서드를 손볼 일이 생기면(예: 경로
탐색 방식이 하나 더 추가되거나, 후보 탐색 로직이 복잡해지면) 1~3번도 같은 기준으로
분리 대상인지 판단한다 — **지금 당장 미리 쪼개두지 않는다**(deletion test와 "2개부터
진짜 seam" 기준에 따라, 실제로 갈라질 이유가 생겼을 때 분리한다).

## 리뷰 체크리스트

새 필드/새 API를 추가할 때:

- [ ] 이 값이 기존 seam 뒤로 들어갈 수 있는가, 아니면 새 seam이 필요한가?
- [ ] 새 seam이 필요하다면, 어디(어느 Service/메서드 경계)에 둘 것인지 먼저 정했는가?
- [ ] 한 메서드 안에서 "왜 이 코드가 여기 있는지" 설명하려면 2개 이상의 다른 이유가
      필요한가? → 그렇다면 분리 후보다.
- [ ] 지금 구현체가 1개뿐인데 미리 인터페이스/추상화를 만들지는 않았는가?
