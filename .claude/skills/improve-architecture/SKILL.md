# 코드베이스 아키텍처 스캔

`rules/backend/module-design.md`의 어휘(Module/Interface/Depth/Seam, deletion test)와
`CONTEXT.md`의 도메인 용어를 기준으로, 얕아진(shallow) 모듈 후보를 찾아 보고한다.
외부 코드/서비스 의존 없이 이 저장소 안에서만 동작한다. 자동 예약 실행은 하지 않으며,
필요할 때 이 스킬을 직접 호출해서 쓴다.

## 절차

### 1. 범위 정하기

- 사용자가 특정 영역(파일/패키지/기능)을 지목했으면 그 영역만 스캔한다.
- 지목이 없으면 `git log --oneline -50`으로 최근 변경이 몰린 파일/디렉토리를 확인해
  핫스팟으로 삼는다. 변경이 고르게 퍼져 있으면 범위를 넓힌다.

### 2. 탐색

`rules/backend/module-design.md`와 `CONTEXT.md`를 먼저 읽는다. `Explore` 서브에이전트로
핫스팟 영역을 훑으며 다음을 찾는다(`module-design.md`의 리뷰 체크리스트를 그대로 적용):

- 한 메서드/클래스 안에서 "왜 이 코드가 여기 있는지"를 설명하려면 서로 다른 이유가
  2개 이상 필요한 지점
- 인터페이스가 구현만큼 복잡한(얕은) 모듈 — 호출부가 내부 조합 순서까지 알아야 하는 경우
- **Deletion test**: 그 모듈/메서드를 지웠다고 상상했을 때, 복잡도가 사라지는지
  (pass-through, 굳이 분리할 이유 없음) 호출부 여러 곳으로 다시 퍼지는지(제 역할을 하고
  있으니 유지하되 인터페이스를 다시 볼 필요)
- DTO에 `with*()` 류 메서드가 계속 늘어나는 패턴(`rules/backend/service.md` "즉시 계산"
  규칙 위반 후보)
- 이미 존재하는 seam(예: 특정 QueryService)이 있는데 재사용하지 않고 비슷한 조회를
  새로 짠 곳

### 3. 리포트 작성

스크래치패드 디렉토리에 마크다운으로 작성한다: `<scratchpad>/architecture-review-<날짜>.md`.

각 후보마다:

- **파일/모듈**
- **문제** — 왜 얕은지, deletion test 결과
- **제안** — 무엇을 어떻게 나눌지, `CONTEXT.md`에 있는 용어로 이름까지 제안
- **강도** — `Strong` / `Worth exploring` / `Speculative`

리포트 맨 위에 "이번에 가장 먼저 볼만한 것" 한 줄 요약을 둔다.

### 4. 전달

리포트 파일 경로를 사용자에게 알려주고, 어떤 후보를 다룰지 물어본다. 사용자가 하나를
고르면 그 후보에 한해 구체적인 리팩토링 계획을 이어간다 — 이 스킬 자체는 스캔과 제안까지만
하고, 실제 구현은 별도로 진행한다(brainstorming/plan 단계부터 새로 시작).

## 하지 않는 것

- 리팩토링을 자동으로 실행하지 않는다 — 리포트와 후보 제시까지만.
- ADR을 자동으로 만들지 않는다 — `domain-modeling` 규칙대로, 되돌리기 어렵고/의외이고/
  실제 트레이드오프가 있었던 결정일 때만, 그것도 사용자에게 먼저 제안한다.
- 스캔 대상이 아닌 파일까지 넓게 훑지 않는다 — 범위를 좁게 유지한다(YAGNI).
