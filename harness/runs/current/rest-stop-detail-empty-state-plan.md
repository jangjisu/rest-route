# Rest Stop Detail Empty State Plan

**Goal:** 휴게소 기본 위치 정보만 존재하고 화면에 표시할 연관 상세 데이터가 전혀 없을 때, 비어 있는 상세 섹션을 나열하지 않고 공통 준비 중 안내를 표시한다.

**Architecture:** 기존 분리 상세 API와 응답 구조는 유지한다. 상세 응답을 조합한 프론트엔드에서 실제 표시 가능한 연관 데이터 존재 여부를 판정하고, 데이터가 없으면 기존 상세 본문 대신 상태 영역에 안내 문구를 표시한다.

**Tech Stack:** JavaScript ES module, Node test runner

## 작업 목표

- `rest_stop`에서 온 휴게소명·노선·좌표·식별자만 있고 표시 가능한 연관 상세 데이터가 없으면 `이 휴게소의 상세 정보를 준비하고 있습니다.`를 표시한다.
- 하나 이상의 연관 상세 데이터가 있으면 기존 상세 화면을 그대로 표시한다.
- 선택 API 실패는 빈 데이터로 오인하지 않고 기존 오류 안내 흐름을 유지한다.

## 변경 스펙

- 상세 데이터 존재 여부는 현재 화면이 실제로 사용하는 다음 정보로 판단한다.
  - 이미지, 주소, 방향
  - 편의시설, 경정비·화물휴게소 운영 상태, 주차 대수
  - EV 충전기, 테마, 진행 중 이벤트
  - 주유 정보, 먹거리, 인기 판매
- 휴게소명·노선·좌표·각종 식별자만으로는 연관 상세 데이터가 있다고 판단하지 않는다.
- 표시 가능한 연관 상세 데이터가 하나도 없으면 상세 헤더의 휴게소명은 유지하고 본문 대신 `이 휴게소의 상세 정보를 준비하고 있습니다.`를 표시한다.
- 표시 가능한 데이터가 하나라도 있으면 현재 상세 섹션 렌더링을 그대로 유지한다.
- 이번 작업에서는 개별 섹션의 부분 데이터 표현이나 백엔드 응답 DTO를 변경하지 않는다.

## 구현 순서

1. 기본 필드만 있는 상세 객체는 비어 있다고 판단하고 각 연관 데이터는 상세 존재로 판단하는 실패 테스트를 작성한다.
2. 집중 테스트에서 예상 실패를 확인한다.
3. 상세 데이터 존재 여부 판정 함수를 최소 구현한다.
4. 상세 성공 상태에서 판정 결과에 따라 본문 또는 준비 중 안내를 표시한다.
5. 집중 테스트와 전체 프론트엔드 테스트를 통과시킨다.
6. 코드·테스트·관련 문서 정합성을 한 번 리뷰하고 하네스 검증 후 커밋한다.

## Trade-off

- 백엔드 응답을 섹션별 상태 구조로 변경하면 의미를 더 명확하게 표현할 수 있지만, 현재 요구사항은 전체 상세 데이터가 비었는지만 판단하면 되므로 API 변경 범위가 불필요하게 커진다.
- 개별 섹션을 모두 재설계하지 않고 현재 화면에 표시 가능한 값만 프론트엔드에서 판정해 기존 동작을 보존한다.
- API 호출 실패와 정상 빈 결과를 완전히 동일시하지 않도록 기존 요청 오류 상태는 유지한다.

## 스펙 영향도

- 스펙 변경 없음 판단 이유: 기존 내부 API 응답, 외부 API 연동, DB 저장 구조를 그대로 사용하고 클라이언트의 빈 상세 화면 표시만 변경하기 때문이다.
- 내부 API: 변경 없음.
- 외부 API: 변경 없음.
- 데이터: 변경 없음.
- 제품: 비어 있는 상세 섹션 대신 사용자에게 하나의 준비 중 안내를 제공한다.
- 아키텍처: 변경 없음. 기존 상세 요청 조합과 렌더링 흐름을 유지한다.
- 기준 문서: 제품·데이터·API·아키텍처 계약 변화가 없어 동기화할 문서가 없다.
