### 무엇을 테스트에 넣고 무엇을 뺐나

기준은 **"사용자 입력 또는 외부 시스템이 실제로 만들어낼 수 있는 상황"**이다.
코드에 방어 분기가 있다는 이유만으로 넣지 않는다 — 방어 코드의 존재가 그 상황이
일어난다는 뜻은 아니고, 그런 분기는 단위 테스트가 덮으면 충분하다.

이 기준으로 뺀 것:

| 뺀 경우 | 이유 |
|---|---|
| 카카오가 좌표에 숫자 아닌 값을 준다 | 카카오 API 계약상 발생하지 않는다 |
| `result_code=0`인데 정점이 하나도 없다 | 계약 위반이라 근거가 없다 |
| `originLat` 파라미터 누락 | 프론트는 위치 없이 이 화면을 쓰지 못해 호출 자체가 안 된다 |

## 여기서 드러난 것

### ① 잘 되고 있는 것

- **비즈니스적 실패는 제대로 구분된다.** 목적지를 못 찾은 것과 경로가 없는 것은 404와
  구체적 안내 문구로 나간다. 결과 코드별 메시지 매핑도 살아있다.
- **readTimeout 10초가 실제로 걸린다.** 15초 지연에 10,018ms — 설정값이 관념이 아니라
  실제로 동작한다는 게 처음으로 측정됐다.
- **에러 본문이 JSON이 아니어도 파싱 실패로 새지 않는다.** 최근 커밋(82c0f03)의 수정이
  실제로 먹고 있다.

### ② 문제 후보

**A. 사용자가 실패를 알기까지 10초를 기다린다**

카카오가 응답하지 않으면 정확히 10초 뒤에 실패한다. 카카오가 이미 5분째 죽어 있어도
**매 요청이 10초씩 새로 기다린다.** 죽은 걸 아는데 계속 문을 두드리는 구조다.

→ 서킷브레이커가 필요한 이유가 교과서 문장이 아니라 이 숫자에서 나온다.

**B. 실패 원인이 하나로 뭉개진다**

500(서버 장애) · 429(쿼터 초과) · 401(키 만료) · HTML 응답이 **전부 같은 결과**가 된다.
대응이 전혀 다른 상황들인데 구분이 없다:

- 429 → 백오프하고 잠시 멈춰야 한다. 더 때리면 더 오래 막힌다
- 401 → 재시도해도 영원히 안 된다. 키를 갈아야 한다. 알림이 필요하다
- 500 → 잠시 뒤 회복될 수 있다

지금은 셋 다 "일시적으로 사용 불가"로 처리되어, **키가 만료돼도 아무도 모른다.**

**C. 재시도가 없다**

10,018ms는 딱 1회 시도다. 재시도가 있었다면 20초·30초가 됐을 것이다.
없는 게 나쁘다는 뜻이 아니라 — **쿼터 있는 API에 재시도를 붙이면 장애 때 쿼터를 더 빨리
태우므로**, 붙일지 말지가 설계 결정이라는 것. 지금은 결정한 적 없이 "없음" 상태다.

**D. 외부 API 실패가 HTTP 200으로 나간다**

`EXTERNAL_API_UNAVAILABLE`이 `HttpStatus.OK`로 정의돼 있다
([ResponseCode.java](../../src/main/java/com/restroute/common/ResponseCode.java)).

프론트가 본문 `code`로 분기하는 설계라면 일관성은 있다. 다만:
- 브라우저·프록시·모니터링 도구는 전부 "성공"으로 집계한다
- 외부 API 장애율을 HTTP 상태로 관측할 수 없다
- 502/503이 정석에 가깝다

의도된 선택인지 확인이 필요하다. 의도라면 그 이유를 문서에 남길 값어치가 있다.

### ③ 아직 못 본 것

- **동시 요청**. 지금은 1건씩만 봤다. 카카오가 느릴 때 요청이 몰리면 커넥션 풀이
  어떻게 되는지 — 지금 Feign은 커넥션 풀 없는 `HttpURLConnection` 기본 클라이언트다.
- **항공권 fan-out**. 요청 1건이 외부 호출 최대 20건으로 퍼지는 경로.
- **지표**. actuator가 없어 위 현상들이 운영 중에는 관측되지 않는다.
