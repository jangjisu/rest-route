# 대표 음식 동기화 및 경로 응답 반영 계획

## 작업 목표

- `origin/main` 기준 새 브랜치에서 대표 음식 API를 전체 페이지 동기화한다.
- 서버 시작 시 빈 테이블이면 초기 동기화하고, 매일 자정에 대표 음식 스냅샷을 갱신한다.
- 대표 음식 원본을 기존 `rest_food`와 분리된 테이블에 저장한다.
- `serviceAreaCode = rest_stop.service_area_code`로 직접 매칭되는 데이터만 경로 휴게소 응답에 연결한다.
- 경로 조회에서 대표 음식은 후보 휴게소 전체를 한 번에 조회해 N+1을 만들지 않는다.
- 프론트엔드와 일반 프로젝트 문서는 변경하지 않는다.

## 구현 계획

1. 대표 음식 외부 API 응답 VO, Feign endpoint, `ExApiClient` 호출을 기존 data.ex 공통 검증·예외 처리 패턴으로 추가한다.
2. 대표 음식 원본 필드와 nullable 내부 연결 키를 보존하는 전용 Entity/Repository를 추가한다.
3. 전체 페이지를 외부 호출 완료 후 수집하고, 모든 페이지 성공 시 트랜잭션 안에서 전용 테이블을 전체 교체한다. 첫 페이지 또는 중간 페이지 실패 시 저장을 시작하지 않아 기존 데이터를 유지한다.
4. 동기화 시 현재 `rest_stop` 코드 집합으로 직접 매칭 키를 계산한다. 매칭되지 않는 행도 원본 데이터로 저장하되 `restStopServiceAreaCode`는 null로 두며, 이름이나 `serviceAreaCode2`로 임의 연결하지 않는다.
5. 시작 초기화기와 일일 자정 스케줄러에 대표 음식 동기화를 추가한다.
6. `RouteRestStopItem`에 `representativeFood(name, price)` 중첩 응답을 추가하고, 후보 코드 목록으로 전용 Repository를 한 번만 조회해 응답에 조합한다. 대표 음식이 없으면 null을 반환한다.
7. 외부 응답·페이지 수집·전체 교체/실패 보존·직접 매칭·방향 필드·경로 응답·일괄 조회·초기화/스케줄러 테스트를 추가하거나 갱신한다.

## 스펙 영향도 확인

| 영역 | 영향 | 내용 |
|---|---|---|
| 외부 API | 변경 | `/openapi/business/representFoodServiceArea`를 새로 소비한다. 기존 `EX_API_KEY`, JSON, 공통 오류 검증을 재사용한다. |
| 내부 API | 변경 | Endpoint: 기존 경로 조회 endpoint. Request: 기존 요청 형식 변경 없음. Response: `RouteRestStopItem`에 nullable `representativeFood`가 추가된다. Error: 기존 경로 조회 오류 형식 변경 없음. 기존 경로 순서·비교·추천 필드는 유지한다. |
| DB 스키마 | 변경 | `rest_representative_food` 전용 테이블과 원본/매칭 인덱스를 추가한다. 기존 `rest_food`는 변경하지 않는다. |
| 제품 범위 | 변경 없음 | 대표 음식 정보를 기존 경로 휴게소 목록에 보강하는 범위다. |
| 프론트엔드/일반 문서 | 이번 작업 제외 | 응답 소비 코드와 API 문서는 후속 작업으로 남긴다. |

## 매칭 및 저장 정책

- 실측 결과 대표 음식 221개 코드 중 현재 `rest_stop`에 직접 매칭되지 않는 코드가 49개 존재한다.
- `serviceAreaCode`를 원본 식별자로 저장하고, 직접 매칭된 경우에만 `restStopServiceAreaCode`에 같은 값을 저장한다.
- 매칭되지 않는 행은 삭제하거나 추정 매핑하지 않고 전용 테이블에 계속 보존한다. 경로 후보 조회에는 포함하지 않는다.
- `serviceAreaCode2`와 `direction`도 원본 값으로 보존한다. `serviceAreaCode2`는 이번 경로 연결 키로 사용하지 않는다.
- 전체 응답 스냅샷이므로 동기화 성공 시 기존 전용 테이블을 교체한다. 전체 페이지 수집이 성공하기 전에는 기존 테이블을 건드리지 않는다.

## 대안과 선택 이유

- 기존 `rest_food`에 대표 음식 필드를 추가하는 방법은 서로 다른 외부 API의 식별자·갱신 주기·보존 정책을 섞으므로 선택하지 않는다. 전용 Entity/테이블로 분리한다.
- 페이지별 즉시 upsert는 중간 실패 시 일부 최신 데이터가 저장되고 이전 행과 혼합될 수 있으므로 선택하지 않는다. 전체 페이지를 먼저 수집한 뒤 성공한 스냅샷만 전체 교체한다.
- 이름 또는 `serviceAreaCode2` 기반 보조 매칭은 현재 전체 데이터에서 직접 일치하지 않는 코드가 확인됐고 오연결 위험이 있으므로 선택하지 않는다. `serviceAreaCode` 직접 일치만 경로 연결에 사용한다.
- 휴게소별 Repository 조회는 route 후보 수만큼 외부 조회가 발생하므로 선택하지 않는다. 후보 코드 목록으로 한 번에 조회한다.

## 리뷰 결론

- DevEx: 외부 API client 계약과 페이지네이션 테스트, 신규 API response field의 nullable 규칙을 확인한다.
- CEO/Design/Security: 제품 방향·프론트엔드·새 보안 경계 변경이 없어 이번 작업에서는 별도 리뷰하지 않는다.
